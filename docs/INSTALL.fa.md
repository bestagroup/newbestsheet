# راهنمای نصب و ارتقا

## پیش‌نیازها

- PHP سازگار با `composer.lock`؛ اجرای بررسی‌ها با PHP 8.3.6 انجام شده است. `composer.json` حداقل PHP 8.2 را درخواست می‌کند، اما ملاک نهایی تمام وابستگی‌های قفل‌شده‌اند.
- افزونه‌های لازم طبق `composer check-platform-reqs`، شامل PDO و درایور دیتابیس مقصد، mbstring، XML، fileinfo، OpenSSL، tokenizer و GD برای CAPTCHA/تصویر. SQLite فقط برای آزمون این تحویل استفاده شده است.
- MySQL/MariaDB مقصد باید ابتدا روی یک پایگاه آزمایشی با همین بسته اعتبارسنجی شود؛ نسخه خاصی در این محیط تأیید نشده است.
- وب‌سرور باید فقط پوشه `public` را document root قرار دهد. کل پروژه، vendor و storage نباید از وب قابل دسترسی عمومی باشند.
- کاربر سرویس باید امکان نوشتن در `storage` و `bootstrap/cache` داشته باشد. دسترسی همگانی 777 لازم نیست.

## نصب تازه روی پایگاه خالی

۱. بسته را باز کنید، وارد `bestsheet` شوید و تنظیمات نمونه را کپی کنید:

```sh
cp .env.production.example .env
```

۲. مقادیر DB، APP_URL، منطقه زمانی و سرویس‌های مورد استفاده را تنظیم کنید. در محیط آزمایشی `MAIL_MAILER=log` و `OPERATIONAL_SMS_ENABLED=false` بگذارید. `APP_DEBUG=false` برای محیط در دسترس کاربران الزامی است.

۳. وابستگی‌های موجود در vendor برای بازتولید آزمون همراه بسته‌اند. روی سرور دارای Composer بررسی کنید:

```sh
composer check-platform-reqs
php artisan key:generate
php artisan migrate --force
php artisan db:seed --force
php artisan system:create-admin
php artisan system:release-readiness --strict
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

در محیط تولید می‌توانید پس از آزمون جداگانه `composer install --no-dev --prefer-dist --optimize-autoloader` را بر اساس همین lock اجرا کنید؛ `composer update` بخشی از نصب این تحویل نیست. حساب مدیر با فرمان تعاملی ساخته می‌شود و رمز پیش‌فرض مشترک ندارد.

## ارتقای نصب موجود

۱. ابتدا نسخه قابل بازیابی از پایگاه داده، `.env`، APP_KEY موجود، storage و اسناد قدیمی بگیرید. بازیابی آن را در محیط آزمایشی امتحان کنید.

۲. این نسخه را در پوشه انتشار جداگانه قرار دهید. `.env` و فایل‌های واقعی نصب قبلی را حفظ و متصل کنید. **برای ارتقا APP_KEY را عوض نکنید و `migrate:fresh` اجرا نکنید.**

۳. بر روی کپی آزمایشی پایگاه واقعی، وضعیت migrationها و تطابق schema را بررسی کنید:

```sh
php artisan migrate:status
php artisan migrate --force
php artisan system:release-readiness --strict
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

migration جدید، دسترسی‌ها و منوهای مجامع و نامه‌ها را اضافه می‌کند. اجرای کل `db:seed` روی نصب موجود توصیه نمی‌شود: seederهای قدیمی می‌توانند تصمیم‌های سفارشی دسترسی سازمان را بازنویسی کنند. اگر migrationهای قبلی قبلاً اجرا نشده‌اند، اثر آن‌ها نیز باید در همان کپی آزمایشی بررسی شود.

۴. migrationهای `2026_10_08` برای جلوگیری از حذف تاریخچه مالی عمداً rollback تخریبی ندارند. برگشت انتشار شامل بازگردانی هماهنگ کد، DB و فایل‌ها از پشتیبان است؛ `migrate:rollback` روش برگشت این تغییرات نیست.

۵. پس از آزمون پذیرش، در پنجره نگهداری ارتقا دهید و workerهای صف را با `php artisan queue:restart` بازراه‌اندازی کنید.

## صف، زمان‌بندی و فایل‌ها

- یک worker تحت مدیر فرایند برای `php artisan queue:work --tries=3` نگه دارید؛ زمان‌های timeout و retry_after را با طول jobها هماهنگ کنید.
- زمان‌بند هر دقیقه `php artisan schedule:run` را اجرا کند. هم‌زمانی worker/زمان‌بند روی زیرساخت واقعی این تحویل آزمایش نشده است.
- اسناد سرمایه‌گذاری در دیسک خصوصی `investment_documents` قرار می‌گیرند. `storage:link` فقط برای دارایی عمومی است؛ اسناد خصوصی را عمومی نکنید.
- برای اسکن، ClamAV و دیتابیس امضای به‌روز را نصب و دسترسی worker را تنظیم کنید. سپس `INVESTMENT_DOCUMENT_ANTIVIRUS=true` و مسیر `DOCUMENT_SCANNER_BINARY` را تعیین و cache تنظیمات را بازسازی کنید. فرمان `php artisan documents:scan --limit=100` هر پنج دقیقه زمان‌بندی شده است. شکست اسکن، فایل را در حالت pending نگه می‌دارد و دانلود مسدود می‌ماند. اسکن واقعی موفق با ClamAV در این محیط تأیید نشده است.
- حذف فایل، حذف نرم است و بایت‌ها باقی می‌مانند. برای حذف فیزیکی و سیاست نگهداری اسناد، روال سازمانی جداگانه لازم است؛ job پاک‌سازی خودکار اضافه نشده است.

## تصمیم‌های لازم برای داده‌های قبلی

- صورت‌های مالی موجود `period_type=legacy` می‌گیرند؛ سالانه/فصلی بودن آن‌ها حدس زده نمی‌شود. پس از تطبیق اسناد، دوره هر رکورد را اصلاح کنید. گزارش را با نوع دوره درست فیلتر کنید.
- در این نسخه مبالغ پرداخت ریالی و عدد صحیح هستند. داده‌های قبلی را از نظر ریال/تومان تطبیق دهید؛ تبدیل خودکار ده‌برابری انجام نشده است.
- اسناد الزامی مراحل باید توسط مدیر فرایند مشخص شوند. تمام اقلام پیش‌فرض الزاماً اجباری نیستند؛ مدرک اجباری باید تأیید شده باشد تا شرط عبور از مرحله را برآورده کند.
- مسیر خام فایل در صورتجلسات قدیمی دیگر به‌تنهایی مجوز دانلود نیست. فایل را به رسانه ثبت‌شده همان پرونده منتقل/متصل کنید و صحت شناسه و دسترسی را بررسی کنید.
- اگر فایل‌های قدیمی از مسیر عمومی سرو می‌شوند، ابتدا به فضای خصوصی منتقل و مراجع آن‌ها تطبیق داده شوند؛ تغییر مسیر دانلود برنامه به‌تنهایی فایل عمومی قدیمی را از وب‌سرور حذف نمی‌کند.
